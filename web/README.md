# Meridian — Next.js app

Single Next.js 16 (TypeScript) app for Meridian Capital v1: UI + API route
handlers in one deployable. See [../docs/PRD.md](../docs/PRD.md). The database
schema is [../docs/DB-SCHEMA.md](../docs/DB-SCHEMA.md), applied verbatim as
`prisma/migrations/0_init/migration.sql`; models in `prisma/schema.prisma` are
generated by `prisma db pull` — never hand-edit them.

## Run

```bash
cd web
npm install
npm run db:migrate            # first time only (needs the DB: docker compose up -d)
npm run db:seed               # first time only: 3 funds, instruments, methodologies, SIP plan
npm run dev                   # starts Postgres automatically (predev hook), app on :3000
```

`npm run dev` starts the Postgres container itself and waits until it's
healthy (predev hook), so day-to-day it's the only command. Stop the DB with
`docker compose stop` from the repo root when done.

`npm run smoke` = end-to-end check against a throwaway `meridian_smoke` DB and
a real `next dev` server: publish → sync fills → verified stamp + omission
flag → close → exit reconciled. `npm run typecheck` for types.

## Docker / deploy (Azure Container Apps)

The repo-root `Dockerfile` builds the production image (Next standalone
output, build context = repo root); its startup command runs
`prisma migrate deploy` (idempotent) before the server, so a fresh database
is migrated automatically. `.github/workflows/deploy.yml` builds the image in
ACR and updates the Container App on every push to main. Locally:

```bash
docker compose --profile app up -d --build   # from repo root: DB + app on :3000
docker compose --profile app stop
```

Plain `docker compose up -d` still starts only Postgres (the app service is
behind the `app` profile so dev flow keeps hot reload). For Azure: push the
image to ACR, set `DATABASE_URL` to the Azure PostgreSQL connection string —
port 3000. Seeding is a manual, dev-only step (`npm run db:seed`), never part
of the image.

## API routes (`src/app/api`)

| Method | Path | What |
|---|---|---|
| GET | `/api/health` | liveness |
| GET | `/api/funds` | funds + latest NAV |
| GET | `/api/funds/:code/nav?from&to` | equity curve + benchmark series |
| GET | `/api/funds/:code/positions` | open positions (claims + verification stamp) |
| GET | `/api/funds/:code/trades?status` | trade feed / closed history |
| GET | `/api/funds/:code/sip-plan?month` | monthly SIP plan |
| POST | `/api/trade-cards` | create draft or publish (stop + exits required) |
| GET | `/api/trade-cards/:id` | card + timeline + reconciliations |
| POST | `/api/trade-cards/:id/publish` | publish a draft |
| POST | `/api/trade-cards/:id/events` | append stop_moved / partial_exit / closed / note |
| POST | `/api/feed/sync` | ingest fills (SnapTrade stub) + run reconciliation |
| GET | `/api/feed/syncs` | sync history (staleness banner source) |
| GET | `/api/reconciliations?status&unresolved` | verification + omission flags |
| POST | `/api/reconciliations/:id/resolve` | trader addresses a flag |
| GET | `/api/instruments/:symbol/news` | AI-ranked news |
| GET | `/api/instruments/:symbol/key-facts` | cached key-facts |

Shared logic lives in `src/lib/` (`db`, `http` error boundary, `domain`,
`reconcile`). No auth yet — that's the next phase, in `src/proxy.ts` (Next 16
renamed `middleware.ts` to `proxy.ts`): paywall, trader role, disclosures.
The reconciler is deliberately naive (48h window, 2% tolerance); the real
agent replaces it after the SnapTrade spike, as a separate worker process.

## Frontend

React/TypeScript pages converted from the HTML prototypes: the landing page
(`src/app/page.tsx`) and the dashboard (`src/app/dashboard/` — fund switcher,
sortable holdings table, Chart.js charts, stock drill-down drawer, dark mode).
The dashboard still renders the prototype's hard-wired demo data
(`dashboard/data.ts`) — wiring it to `/api` is the next frontend task.
